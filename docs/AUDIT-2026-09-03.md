## Summary

The verdict is **B — ready for SESSION 13 with targeted remediation**, and nothing
below argues for restructuring. Re-run against the actual repository, the
project's safety properties hold and are enforced by code, not merely
documented: the 18-contract gateway rejected all seven adversarial records
thrown at it (arbitrary JSON, an unknown contract, an empty body, an extra
field, `null`, a string, an array); a live Source Scout run against all five
registered EU endpoints, blocked by the session's egress policy, produced five
`DataGap` records and zero false-positive candidates; every agent's own suite
hashes the whole of `data/` around a full run against the real corpus and
asserts byte-identity, and this audit's own real runs (Scout mock and live,
Verifier, Integrator, Detector, Depth, the gap router) left it untouched.

What blocks SESSION 13 specifically is narrower than the debt surface: a
knowledge graph is a structure of stable nodes and durable edges, and three
findings are exactly that structure's prerequisites, missing across every
agent that writes a record — Scout, Verifier, Integrator, Detector, Depth, and
now the gap router. None require a schema change or touching `data/`.

## P1 — blocks SESSION 13 specifically

### F-18 · Record ids have no identity beyond the run that minted them

All six record-producing agents mint ids from a per-run counter —
`#id(prefix) → prefix-NNN`, or the bucketed equivalent in the gap router:

```
agent/depth/depth.mjs:109        #id(kind)     → kg-<kind>-NNN
agent/detector/detector.mjs:101  #id(prefix)   → <prefix>-NNN
agent/integrate/adapter.mjs:86   #id(prefix)   → <prefix>-NNN
agent/scout/scout.mjs:117        #id(prefix)   → <prefix>-NNN
agent/verifier/verifier.mjs:104  #id(prefix)   → <prefix>-NNN
agent/proposals/data/proposals.mjs:109  #id(kind, bucket) → <kind>-NNN, per-bucket counter
```

Run the same analysis twice and every id changes. Measured against the real
corpus: 57 `KnowledgeGap` records, 57 distinct `gap_id`, but only **56
distinct** `(gap_kind, entity)` natural keys —
`missing_instrument_relationship|ai-act` collides, so even the obvious
fallback key is not quite sufficient on its own. A knowledge graph is
precisely a structure of stable nodes; this is the specific prerequisite it
does not have.

**Recommended direction:** derive each id from the record's own content — kind
or type, plus the full sorted affected-entity set, plus subject — rather than
a counter. Do not add an id lookup store: a table mapping old ids to new would
be the second home this architecture's own "one home per fact" principle
exists to prevent.

### F-19 · No agent CLI populates cross-agent trace linkage

`Span.handoff()` (`agent/observability/tracer.mjs`) and `gateway.handoff()`
(`agent/schemas/gateway.mjs`) exist and are implemented correctly, but the
only callers outside test suites are in `agent/observability/demo/workflow.mjs`
— a fixture, never a real run. Confirmed twice: by chaining a real Scout trace
into a real Verifier run (`agent/verifier/cli.mjs --records <trace-id>`), whose
resulting `AgentRun` came back `parent_run_id: null`, `handed_off_to: []`, with
**zero** references anywhere in its trace to the Scout trace it consumed; and
by inspecting the gap router's own `--gaps <trace-id>` flag
(`agent/proposals/data/cli.mjs`), which reads a Depth run's records but neither
sets `parent_run_id` on its own `AgentRun` nor calls `handoff()`. "Can this
execution be correlated with another agent's?" — observability requirement 7 —
is unanswerable in every real code path today, on either side of the gap
router.

**Recommended direction:** in every CLI that accepts `--records`/`--gaps
<upstream-trace-id>`, pass that trace's run id through as `parent_run_id` on
`startRun`, and call `handoff()` on the upstream span when accepting its
output. The contract fields (`parent_run_id`, `trace_ref`, `handed_off_to`)
already model this correctly on every relevant contract; only the CLIs fail to
populate them.

### F-20 · A run whose entire input was refused at intake still reports `ok`

In the chained Scout → Verifier run above, all six candidates were correctly
refused (`simulated` records are never actionable — the refusal itself is
correct and must not be relaxed); six child spans closed `failed`; six `error`
records were written — and the root span still closed `status: ok`, and
`agent/observability/cli.mjs list` still renders `✓ ok`. The per-record
epistemics are honest — the `AgentRun`'s `epistemic.unresolved` names all six
refused candidates — but the aggregate signal is not. `degraded` is already
defined in `agent/observability/schema.mjs`'s status vocabulary and computed
at read time in `query.mjs` for exactly this shape (a root closing `ok` over
one or more failed children); it does not reach the summary line in
`cli.mjs list` or drive the process exit code. In a scheduled context this is
indistinguishable from "nothing to do."

**Recommended direction:** surface `degraded` in the run summary read model,
and give total-intake-refusal a non-zero exit in the affected CLIs.

## P2 — worth doing soon, not gating

### F-21 · No trace carries a commit sha or code version

No span, on any agent, carries a git sha or version attribute. "Which code
state ran" — observability requirement 2 — is unanswerable from any trace.
`Tracer` already accepts free-form `attributes`; no CLI populates one with a
commit sha at construction.

### F-22 · The Scout → Verifier boundary has never been exercised with a real record

Every transition between agents has been verified either within one agent's
own adversarial fixtures, or — for Scout → Verifier — attempted for real and
correctly refused, because the only real Scout output available (mock or a
live run blocked by egress policy) is `simulated`, and `simulated` records are
never actionable by design. There is no path that keeps a real record's
`simulated` flag propagating end to end without laundering a fixture into
something that looks real. This is not a defect to fix by weakening the
refusal; it is an untested surface to note.

  wildcard reference as resolving, unconditionally.

## What was verified as genuinely sound (do not re-litigate)

- **The contract gateway rejects malformed input.** Tested adversarially: raw
  JSON with no `contract` field, an unknown contract name, a known contract
  with an empty body, a known contract with an extra unrecognised field,
  `null`, a bare string, an array — **7/7 correctly rejected** by
  `agent/schemas/gateway.mjs`. No skip flag exists.
- **A failed retrieval becomes a `DataGap`, never a candidate.** Verified
  against the real network: `agent/scout/cli.mjs --live --dry` against all
  five registered EU endpoints, blocked by the session's egress policy,
  produced **5 gaps, 0 candidates, 0 false positives.**
- **`simulated` records are correctly refused as never-actionable.** The
  refusal that blocked F-22 above is the feature working, not a bug.
- **The CI write boundary holds.** `.github/workflows/source-scout.yml`'s
  two-job split (network access with no write token / write token with no
  network beyond github.com), `agent/scout/schedule/guard.mjs` as an allowlist
  enforced on both sides of the artifact boundary, attacker-controlled inputs
  bound to `env:` and never interpolated into shell.
- **No agent writes to `data/`.** Every suite hashes the directory before and
  after a full run against the real corpus and asserts byte-identity; this
  audit's own real runs across all six agents left it untouched.
- **`data/brief.json` vs. `index.html`'s inline `__CONTENT__` drift is real
  and already documented (`docs/AUDIT-2026-09-01.md` F-04).** Independently
  re-measured: `meta.standfirst` differs between the two homes; nothing loads
  `brief.json` at runtime. Not a new finding.
